Overall, this is a good, careful implementation, especially for a homework assignment. It is readable, decomposed sensibly, and much more defensive than a typical matrix-vector multiplication solution. I ran the program as written: the 1000×1000 case passes, with a maximum difference of about 5.0e-12 from its reference calculation.

What is good

The separation into _validate_sequence(), dot_product(), and matrix_vector_multiply() is excellent. Each function has a clear responsibility, and matrix_vector_multiply() correctly builds the output from row-wise dot products.

The dimension checking is also good. This prevents something like a 3-element matrix row from being multiplied by a 4-element vector and gives a useful error telling you which row was wrong.

I particularly like that the vector is validated once rather than once for every matrix row. For a 1000-row matrix, that avoids checking the same 1000 vector elements another 999 times.

Your main() is also thoughtfully constructed: fixed random seed for reproducibility, a reasonably large test case, timing, result inspection, and a separate reference calculation.

There are, however, a few things I'd change.

1. There is an actual bug in the "sequence" validation

This comment says the check catches dictionaries:

    # Catches None, plain numbers, sets, dicts, and generators

But it doesn't.

A dictionary has both __len__ and __getitem__, so this passes:

    dot_product({0: 1, 1: 2}, [3, 4])

and your function actually returns:

    11.0

Even stranger:

    dot_product({"a": 1, "b": 2}, [3, 4])

raises:

    KeyError: 0

rather than the documented TypeError.

So I would explicitly reject mappings:

    from collections.abc import Mapping

    if isinstance(seq, (str, bytes, bytearray, Mapping)):
        raise TypeError(...)

Or, if this assignment only expects lists/tuples, simplify aggressively:

    if not isinstance(seq, (list, tuple)):
        raise TypeError(...)

For homework code, I actually prefer the second approach. It is easier to reason about and doesn't pretend to support arbitrary Python objects.

2. Your definition of "real number" doesn't quite match the implementation

Your docstring says:

    sequence of real numbers

but you specifically accept only:

    (int, float)

and deliberately accept bool.

So this is valid according to your program:

    dot_product([True, False], [10, 20])

and returns 10.0.

Python technically considers bool a subclass of int, so this is legal, but mathematically I would find it surprising for a linear-algebra function.

I'd probably reject booleans:

    if isinstance(value, bool) or not isinstance(value, (int, float)):
        raise TypeError(...)

Unless you intentionally want Boolean vectors.

3. Very large integers reveal another validation problem

This line looks harmless:

    if not math.isfinite(value):

but Python integers can be arbitrarily large.

For example:

    dot_product([10**400], [1])

currently produces:

    OverflowError: int too large to convert to float

inside the validation.

That contradicts the documentation saying validation raises TypeError for bad types and ValueError for non-finite values.

Since integers cannot be NaN or infinity, a simple solution is:

    if isinstance(value, float) and not math.isfinite(value):
        raise ValueError(...)

No need to call math.isfinite() on ordinary integers.

4. The overflow explanation is slightly mathematically incorrect

This is the most interesting issue.

You say:

    # the true result overflowed float range during accumulation.

and the docstring says:

    "If the true dot product is too large to represent as a float..."

But consider:

    vec1 = [1e308, 1e308]
    vec2 = [2.0, -2.0]

Mathematically,

    (10^308)(2) + (10^308)(-2) = 0

So the true dot product is zero.

But floating-point arithmetic computes:

    1e308 * 2 → inf
    1e308 * -2 → -inf
    inf + -inf → nan

and your program raises the overflow error.

The check itself is reasonable. The explanation is what should change.

Instead of:

    raise OverflowError(
        "dot product overflowed the range of a float"
    )

I'd say:

    raise OverflowError(
        "dot product produced a non-finite result during floating-point arithmetic"
    )

That's technically accurate.

5. I don't love _validated=False

This is clever:

    def dot_product(vec1, vec2, _validated=False):

and I understand exactly why you did it: matrix_vector_multiply() has already validated everything, so don't redo the work.

But now anybody can do:

    dot_product(bad_data, other_bad_data, _validated=True)

and completely bypass your safety checks.

For internal code, I'd rather have:

    def _dot_product_unchecked(vec1, vec2):
        total = 0.0
        for i in range(len(vec1)):
            total += vec1[i] * vec2[i]
        return total

Then:

    def dot_product(vec1, vec2):
        # validate
        return _dot_product_unchecked(vec1, vec2)

and:

    def matrix_vector_multiply(matrix, vector):
        # validate
        ...
        result.append(_dot_product_unchecked(row, vector))

That makes the public function impossible to accidentally call in "unsafe mode."

For a homework assignment, though, I might go even simpler and accept the small repeated-validation cost rather than introducing additional machinery.

6. The "independent" test isn't as independent as the comment suggests

You wrote:

    expected = [
        sum(a * b for a, b in zip(row, vector))
        for row in matrix
    ]

which is absolutely a useful cross-check.

But both implementations effectively perform:

    a0b0 + a1b1 + ... + anbn

in essentially the same floating-point order. So they could share certain numerical problems.

I'd supplement the random test with small cases whose answers are known beforehand:

    assert dot_product([1, 2, 3], [4, 5, 6]) == 32

    assert matrix_vector_multiply(
        [[1, 2], [3, 4]],
        [5, 6]
    ) == [17, 39]

And test failures deliberately:

    # mismatched vectors
    dot_product([1, 2], [1])

    # mismatched matrix row
    matrix_vector_multiply([[1, 2, 3]], [1, 2])

    # NaN
    dot_product([1, float("nan")], [2, 3])

Those tests actually exercise your validation logic, which is currently the most complicated part of the program.

7. Minor improvement: use time.perf_counter()

You currently use:

    start_time = time.time()
    ...
    elapsed = time.time() - start_time

For benchmarking elapsed execution time, Python's preferred timer is:

    start_time = time.perf_counter()
    ...
    elapsed = time.perf_counter() - start_time

Not a correctness issue at all—just a better clock for measuring durations.

The bigger question: is the code over-engineered?

A little bit.

For an assignment whose requirements appear to be essentially:

    write a dot product using a for loop, use it for matrix-vector multiplication, and test it with a random 1000×1000 matrix

your validation infrastructure is almost as complicated as the actual algorithm. The core mathematical code is only:

    total = 0.0
    for i in range(len(vec1)):
        total += vec1[i] * vec2[i]

and:

    result = []
    for row in matrix:
        result.append(dot_product(row, vector))

The extra validation is intellectually good, but every added feature creates additional behavior that itself needs to be correct—and we've already found two edge cases in that layer.

So my preferred version would keep the good structure but simplify the contract considerably.

What I would change, in priority order

1. Fix the dictionary/sequence-validation bug.
2. Decide explicitly whether bool should count as a number. I would reject it.
3. Fix math.isfinite() for arbitrarily large integers.
4. Change the overflow explanation so it doesn't claim the exact mathematical result overflowed.
5. Remove _validated from the public-facing dot_product() interface.
6. Add several deterministic edge-case tests instead of relying almost entirely on the 1000×1000 random test.
7. Switch from time.time() to time.perf_counter().
8. Consider trimming some comments/docstrings—the code is readable enough that several comments repeat what the next line already says.

Bottom line: the actual matrix/vector algorithm is correct and clean. The weaknesses aren't in the linear algebra; they're mostly consequences of trying to make the input-validation system unusually sophisticated. For BMI 500 homework, I'd simplify that layer slightly rather than adding even more defensive machinery.
